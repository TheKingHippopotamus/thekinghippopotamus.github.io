How the work is run

Everything on this site is built and verified on a single Linux server that I run the way a small engineering office is run: with standing procedures rather than one-off commands.

A scored security audit engine runs on a schedule and grades the host against its own baseline, so drift shows up as a falling number instead of a surprise. The container control plane is bound to the loopback interface and reachable only through an authenticated tunnel, which means no orchestration surface is exposed to the public internet at any point. Every consequential change is written to an append-only decision log before it is made, so the reason for a configuration is recoverable months later by reading rather than guessing.

A publish gate sits in front of anything that leaves the machine. It refuses a push when the diff contains a credential, an internal hostname, a private address range or a local filesystem path, and it fails the build rather than stripping the match quietly. The generator behind this site runs the same gate against its own output: a URL that is not on the allowlist, or an identity pattern anywhere in the built pages, aborts the build.

The method is the point. Agents write most of the implementation code; the specifications, the review gates and the acceptance criteria are mine, and nothing is published until the check has been re-run and recorded.

I design, direct and verify multi-agent systems: I write the specifications, review gates and acceptance criteria; most implementation code is generated by AI agents under my review; every claim here was re-run and recorded before publication. Where a component is hand-written, the case study says so.
