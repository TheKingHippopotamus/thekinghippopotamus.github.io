Case study

Automation & reliability engineering

Fifty-four scheduled jobs on one host, and a watcher engineered so that a defect in the pipeline cannot take down the thing watching it.

Context

The failure mode this estate is built against is not a crash. It is a job that quietly did not run, a source that was never fetched, or a counter that lied — found mid-project, after something has already been built on the hole. The written doctrine names the disease in its own words: absence of data mistaken for knowledge about the world.

So the practice is a ledger, not a README. It holds 370 incident records across 96 subsystem areas in a fixed shape — timestamp, area, fault, cause, fix, automation, status — and the last two fields are the argument. An incident is not closed by a fix; it is closed by the check that would have caught it. Eighteen rows have reached that state. 114 are fixed, 20 carry a resolution, and 218 are open and visibly so.

The second half of the practice is that nothing may be silent. Every check mails. A check that finds a gap exits differently from a check that broke. And the thing that watches the nightly build is not permitted to depend on the nightly build.

What I built

Everything scheduled is a declared unit, not a script someone remembers to run. Fifty timer files were written by hand; the scheduler has 43 timers loaded and running, alongside 11 cron lines for the jobs whose sub-hourly or market-close semantics cron expresses better — 54 jobs in all. The unit file is where the reliability semantics live: 44 of the 50 catch up a firing missed during downtime, 29 start on a randomised delay so nothing stampedes one host, and 8 are pinned to the US market clock, because daylight-saving drift is a proven bug class here. Seventeen of the 50 are guards or hygiene rather than collection.

Guards do not run on hope. A census exits with a distinct status when it finds a gap, and its unit declares that status a success, so "found a problem" is never read as "crashed" — 29 of 61 service units say so explicitly. Underneath, the host sensor makes 96 full ten-layer passes and 288 three-layer passes a day, plus an hourly janitor and an hourly check that the outbound-only posture has not been altered; the 06:00 digest folds the layers into one message.

I built a local CI runner this week, because hosted CI is not available to this estate: a per-repository test run, plus a nightly check that installs each published Python release into a clean environment, runs its CLI and imports it, and installs the two npm packages into a throwaway project and resolves their entry points. Test suites stand green at 245, 157 and 16, fresh install passes on all three Python releases, and the end-to-end run is 15 pass / 1 fail — the one failure is the harness's own outbound-link check, which flags every external link the site carries.

Watcher independence — the watcher reads artifacts, never the pipeline

Decisions

  • Chose declarative timer units over cron one-liners because the unit file is the one place restart, catch-up and drift semantics can be stated and then counted: 44 of 50 catch up after downtime, 29 randomise their start, 8 pin to the US market clock. Cron kept only the 11 jobs it expresses better.

  • Chose a watcher that reads artifacts over a watcher that imports the pipeline because a defect in the pipeline must not be able to disable the thing that watches it: 205 lines, standard library only, no pipeline import, and scheduled twenty minutes later so it inspects a result rather than racing one.

  • Chose a distinct exit status for "found a gap" over a generic non-zero failure because a scheduler otherwise cannot tell a working check from a broken one — which is why two finance-scope units sit in a failed state by design, holding findings, instead of quietly succeeding. The convention has its own failure mode, on record here: an argument-parsing error that also exits 2 reads as success, which is how one weekly job failed quietly until the mismatch was found.

Limitations

  • One host. No failover, no replica, no second scheduler. What is demonstrated here is detection and recovery discipline, not availability engineering — and not uptime.

  • The register is disciplined, not clean. 218 of 370 incident rows are open and only 18 are closed by an automation. At the moment of audit five user-scope units were in a failed state: two finance-scope units holding findings by design, exiting non-zero rather than crashing, and three inert leftovers.

  • Coverage of the watchers is itself incomplete, and known to be. The August mail audit turned up a service that had been failing silently because its working directory no longer existed, and a job that hung for two hours with no check to notice.

  • No aggregate mean-time-to-detect has been measured. Two latencies are defensible — a reboot race alerted within the same boot cycle, and a reconciliation warning fired every morning until it was root-caused — but there is no estate-wide figure.

  • An empty alert log is not proof the pipeline never missed a night. Weekends, market holidays and deliberately silent days are excluded by design, and the switch has never been observed to fire. Nor is the change guard self-healing: it repairs a narrow enumerated set of mechanical defects and escalates everything else.
