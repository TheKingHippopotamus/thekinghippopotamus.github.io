Case study

Products & developer tooling

Every documented claim on the three Python packages I publish runs as a command, with a recorded output and one of three verdicts.

Context

Publishing to a registry is a promise made to someone I will never meet, and it is kept or broken at install time, on a machine I never see.

Three of these packages exist because I needed them. The CAD automation server exposes a modelling application's geometry, scripting and visual-programming surface as MCP tools, so an assistant can drive the model instead of a person clicking through it; it is for anyone who already runs that application. The vault is a local-first credential store for someone who wants their passwords on their own disk, with no account, no sync and no server to trust. The XBRL server wraps a mature filing processor so SEC filings can be queried as tools; its first consumer is my own research pipeline, and a transport fault found from that consumer's seat was filed as an incident against my own package, fixed, and shipped in the released version — full record on request.

Then I audited all three the way a stranger installs them.

What I built

The rule is one line: clone, install, run — nothing taken from the README on trust. Every documented claim becomes a shell command with a recorded output and one of three verdicts: held, failed, or not testable. The vault audit runs 22 claims that way; the CAD server audit runs five headline claims plus a census.

CAD server, 0.2.2. Each request carries a correlation identifier that is compared against the reply, the timeout path closes the socket, and the client reconnects only where a connection has already succeeded, so a slow operation cannot hand its answer to the next call. 89 tools counted at runtime, from a registry the package's own test reads; 245 tests, of which the 16 integration tests skip for want of the application. Every runtime dependency carries an upper cap with the reason written beside it; the 3-operating-system × 4-Python matrix carries a weekly schedule. The container image starts and waits on stdin.

Vault, 3.2.2. The packaging summary names the cipher the code runs, and a test pins the key derivation at both sites so the two cannot drift. 157 tests, most of them a static scan asserting that no module names a networking symbol. The self-destruct reports failure when the keychain entry survives it.

XBRL server, 2.1.1. Logging is held off the transport by three guard layers — file descriptor, Python object, logger — so no library write can corrupt JSON-RPC framing. 46 tools, 16 tests.

A nightly check reinstalls every published package into a clean environment — the three Python releases get their command line run and their module imported, the two browser elements get installed from the registry and their entry point resolved; all five pass.

The method: a claim, the command that tests it, the recorded output, one of three verdicts

Decisions

  • Chose to vendor the wire-protocol module twice — once for modern Python, once for the CAD application's stdlib-only embedded interpreter — over one shared compatibility shim, because the embedded half cannot install anything and a shim would have had to be judged against modern lint and type rules on both sides; instead each copy pins the same wire contract — a 4-byte big-endian length prefix, UTF-8, a JSON object body, a 64 MB ceiling — and the lint config excludes the old-dialect half by path.

  • Chose a machine-checkable assertion over a corrected string wherever documentation and code can disagree, because a corrected README drifts again in a month: the XBRL server reads its tool count from the live registry and fails any README or instruction string that disagrees, and the vault carries a banned-claim grep that must exit 1.

  • Chose to cap every runtime dependency and add a weekly scheduled matrix run over trusting a lower bound, because dependency drift is invisible to a workflow that only fires on a push — but the cap is the half that holds today: hosted workflow runs are not available on this account, so the schedule is a file waiting for a runner rather than a control that is running, and the releases were built and uploaded from the same host that runs the tests.

Limitations

  • Shipped today, not soaked. The index carries 0.2.2, 3.2.2 and 2.1.1, uploaded within minutes of each other; the CAD server and the XBRL server are tagged on the public repository, the vault carries its version in the package with no tag. The nightly reinstall check passes on all three from a clean environment, but one clean run on release day is not a soak, and nothing here has been running long enough to drift. The vault figures on this page were taken at 3.2.1 and re-checked against 3.2.2 before publication.

  • The build and release path is local, not hosted. Hosted workflow runs are not available on this account, so these releases were built and uploaded from the same host that runs the tests, and the weekly dependency schedule is correct as a file that has never fired.

  • 157 self-authored tests are not a security audit. No independent third-party review of the vault exists, and its own README says so. The self-destruct is a single in-place overwrite followed by unlink — wear-levelling, copy-on-write filesystems and journaling can all leave the original blocks, filenames and directory entries are not overwritten, and hardlinked copies are not handled. The biometric check is an advisory boolean from a subprocess exit code; the key is released by an unconditional keyring read.

  • No adoption is claimed or measured. No download figures were taken, no issues are open against these packages, and nothing here says anyone else runs this code.

  • The watchdog CLI, the financial-data CLI and the earnings scanner are repositories, not products. None is published to a registry, two of the three carry no CI workflow at all, and their README figures are self-reported and were not re-measured here.
