Case study

Security operations & governance

A ruling checks the live host before it decides. Both layers write to one audit trail. The publish gate can refuse.

Context

One host carries the client work, the financial data, the automation and a public identity. There is no staging tier and no containment tier, so every severity call is made against a total blast radius, and the severity policy is written that way.

The register is the spine. Each entry is numbered and carries a severity, a state and the date it was last checked against the live host. Entries close by re-checking, not by time passing, and where an entry has never been checked the register records that rather than carrying a date.

Two rules govern how the register is used. A live check outranks memory — a register is a record of what was true when somebody last looked, so a resumed session re-runs the line before acting on it. And the officer function is separated from the execution function. One layer decides what tasks exist and what severity they carry; the other runs the runbooks. Both write through the same event dispatcher, so there is one trail rather than two — and the dispatcher records an event type it does not recognise as an unknown event rather than quietly accepting it as a known one.

What I built

A ruling has a fixed four-part shape, and the checking comes before the verdict. The most recent one opens with six live checks run against the box rather than against the register, states the verdict in one paragraph with the residual risk named by class, attaches twelve numbered requirements all marked mandatory, and closes with an eight-item post-arm checklist to be run attended — output pasted into the record before the surface counts as live. Arming without the checklist is a breach of the ruling, not a shortcut.

Three mechanisms do the load-bearing work under it.

Inbound is denied at two independent layers, because the container daemon writes its own firewall chain that is consulted before the host chain — a rule in one place only is a rule that can be walked around.

A silent configuration override was neutralised by ordering rather than deletion. The daemon resolves directives first-value-wins, and a vendor-supplied drop-in was being read before the administrator's own file, so the intended setting never applied and reading the main file would never have shown it. A second drop-in, named to sort ahead of it, is read first and wins. The replacement access path was demonstrated live first, timestamped, before anything was changed.

Untrusted documents are converted only through a wrapper: safe mode, a throwaway per-call profile, a sandbox with private temp and process isolation. Where a separate network namespace was unavailable, a 92-line seccomp filter enforces the same denial one layer down, refusing internet-family sockets outright.

Nothing here has been tested by an adversary.

The anatomy of a ruling — four parts, and the register entry it creates the same day

Decisions

  • Chose to deny inbound at two independent layers over one clean rule in the host firewall, because the container daemon writes its own chain that is consulted before the host's user chain — a single rule in the wrong layer is bypassed by the layer above it.

  • Chose to neutralise a silent configuration override by adding a drop-in that sorts ahead of the vendor file over deleting that file, because the daemon resolves directives first-value-wins and the earlier-sorting drop-in is therefore the one read first: deletion fixes today and re-breaks on the next provisioning event, while ordering makes the intended value win either way — and the ruling carries a standing watch item to re-read the resolved configuration, not the file, after any provider event.

  • Chose to make a missing secret scanner a hard failure with no opt-out flag over letting the gate skip a check it could not run, because a scan that did not run did not pass — the one optional check reports WARN inside a loud block and the documentation states WARN means the check produced no findings to show, never coverage.

Limitations

  • Nothing here is a penetration test, a third-party review or a certification. Every finding is self-assessed and the documents say so. The claim is a documented posture, not an absence of compromise — the incident log holds two confirmed incidents.

  • The sensor score is not a coverage figure and must not be read as one. The register entry that carries it records that the headline score overstates real coverage, so a green reading is not evidence of coverage. Re-baselining is deliberately manual, which is what makes an unexplained change meaningful and what makes a stale baseline possible.

  • The controls on the automation surface are procedural by design: they are written rules that agents consult, and this page claims no technical enforcement layer behind them.

  • This is not continuous monitoring with forensic readiness. Forensic coverage is carried on the register as an open item, not a closed one. Alerting is deliberately wrapped so a delivery failure cannot break collection, which also means a failed alert is silent.

  • The container control plane is built and checked, not permanently deployed. Of the seven residual risks its own security document publishes against itself, three are still open, and the one recorded as closed is closed pending a live re-check that has not been run.

  • The gate is the required last step before this site is published, not a guarantee about everything already public. Artifacts published before the gate existed never passed through it, and nothing the gate does can retract what was already distributed.
